Enterprise Entity-Relationship Diagram (ERD) SIWRMS — Complete Logical Data Model Design Precedes: Physical DB / SQL / ORM / Implementation Role: Principal Enterprise Software Architect Base: SRS v1.0 + BRF v2.0 + BPQ + Domain Model (with two corrections) Date: 2026-07-23 Status: ERD Design Only — No Code, No SQL, No ORM 0. GOVERNING DESIGN DECISIONS These apply to every table unless noted: 0.1 Domain-Model Corrections Applied Inventory is NOT an aggregate root and NOT a stock table. There is no inventory table holding editable balances. Stock is always a derived projection computed from immutable inventory_transaction rows. A read-optimized inventory_balance_snapshot view/table may exist as a non-authoritative cache only. Customer is its own Aggregate Root with its own table and identity, not nested under Representative. 0.2 Universal Audit Fields (every table stores these) Field Type intent Notes id Surrogate PK (UUID/GUID) Global unique per row created_at timestamp (UTC) Set on insert created_by user_id FK Inserting actor updated_at timestamp (UTC) Set on every update updated_by user_id FK Last updating actor deleted_at nullable timestamp Soft-delete marker version integer / row-version Optimistic concurrency token Soft delete (deleted_at) is supported wherever appropriate (master data, config). Append-only / History tables do NOT use soft delete — they are immutable and never removed; see normalization note §N1. 0.3 Immutability / History Tables Append-only tables (inventory_transaction, *_history, audit_log, price_history, purchase_price_history, order_status_history, transfer_history, invoice_history, approval_history, shipment_status_history, bot_message_log) disable UPDATE and DELETE at the permissions layer. Corrections = a new compensating row. 0.4 Table Classification Legend M = Master Data (business entities slow to change) T = Transactional (event/incident records) R = Reference (lookup, enum-backed, controlled vocabularies) C = Configuration (tunables, policies, rules) H = History (immutable append-only change records) J = Junction (resolution of N:N relationships) V = Projection/View (read-optimized, non-authoritative — clearly marked) 0.5 Naming Conventions Tables: snake_case, singular noun (e.g. product, order). Junctions: a_b (alphabetical) or verb form (order_line, customer_rep_assignment). History: explicit _history suffix for mutable-master change logs; append-only event tables named directly (inventory_transaction, audit_log). All cross-references by surrogate id. Business keys used only in unique constraints. PART A — ENUMS (Identified Separately) Enums are not stored as tables; they are enumerated value sets enforced by CHECK constraints. Listed here for schema clarity. (Where the business needs runtime editability, the enum is instead promoted to a *_type Reference table — flagged below.) F.6 — FINANCE / INVOICING (continues from T16)

T17 — invoice Purpose: Invoice header generated from one or more shipped/fulfilled orders (BR-F1, SRS E19). PK: id FK: customer_id → customer, currency_id → currency, created_by → app_user Important fields: invoice_number (unique), state (InvoiceState), subtotal, tax_total, discount_total, grand_total, amount_paid (derived cache), balance_due (derived cache), issued_at, due_at, closed_at Unique: invoice_number Business constraints: an invoice may aggregate lines from multiple orders — resolved via invoice_order (J1); once state = PAID or CLOSED_CORRECTED the header and its lines are immutable, corrections are issued only via credit_note (T20); amount_paid/balance_due are read-optimized caches reconciled from payment_allocation (J2), never edited directly Classification: T

T18 — invoice_line Purpose: Line items of an invoice; price frozen at issue time (BR-P3, SRS E20). PK: id FK: invoice_id → invoice, order_line_id → order_line (nullable — allows non-order lines e.g. freight, manual adjustment), product_id → product (nullable for non-product lines) Important fields: description, qty, unit_price (frozen), tax_rate, tax_amount, discount_value, line_total Unique: (invoice_id, order_line_id) where order_line_id is not null Business constraints: unit_price copied from order_line.unit_price at issue time and never re-resolved against price_history; immutable once invoice is ISSUED Classification: T

H4 — invoice_history Purpose: Immutable state-change log for invoices (same pattern as order_status_history T12, transfer_history T6, shipment_status_history T16). PK: id FK: invoice_id → invoice, actor_user_id → app_user Important fields: from_state, to_state, event_at, note Unique: n/a (chronological append) Classification: H

J1 — invoice_order Purpose: Resolves the N:N relationship between invoice and order — one invoice may bill multiple orders, and (split-invoicing) one order may be billed across multiple invoices (BR-F1). PK: composite (invoice_id, order_id) FK: invoice_id → invoice, order_id → order Important fields: linked_at Unique: (invoice_id, order_id) Classification: J

T19 — payment Purpose: Money received from a customer (SRS E21), recorded independently of any single invoice to support pre-payments and over-payments. PK: id FK: customer_id → customer, currency_id → currency, received_by → app_user Important fields: payment_number (unique), amount, method (PaymentMethod), reference (bank ref / cheque no.), received_at, unallocated_amount (derived cache) Unique: payment_number Business constraints: immutable once posted; a payment can exceed a single invoice and be split across several via payment_allocation; corrections via a compensating reversal payment, never an edit Classification: T

J2 — payment_allocation Purpose: Resolves N:N between payment and invoice — a single payment may settle several invoices, and an invoice may be paid via several payments (BR-F2, EC10: partial payments allowed). PK: id FK: payment_id → payment, invoice_id → invoice Important fields: allocated_amount, allocated_at, allocated_by → app_user Unique: (payment_id, invoice_id) Business constraints: Σ(allocated_amount) per payment ≤ payment.amount; Σ(allocated_amount) per invoice ≤ invoice.grand_total; invoice.state (PARTIALLY_PAID / PAID) is recalculated from allocation totals, never set directly Classification: J

T20 — credit_note Purpose: Formal correction instrument against a closed/issued invoice — returns, pricing errors, disputes (BR-F3, EC11, SRS E22). Never edits the original invoice. PK: id FK: invoice_id → invoice (the invoice being corrected), customer_id → customer, issued_by → app_user, reference_type + reference_id (nullable, polymorphic link to the originating return/adjustment) Important fields: credit_note_number (unique), reason_code_id → reason_code_ref, total_amount, state (DRAFT/ISSUED/APPLIED/VOID), issued_at Unique: credit_note_number Business constraints: reduces the customer's balance via a customer_ledger_entry (T22), never mutates invoice rows directly; applying a credit_note marks the original invoice CLOSED_CORRECTED Classification: T

T21 — credit_note_line Purpose: Line items of a credit note, mirroring the invoice lines being corrected. PK: id FK: credit_note_id → credit_note, invoice_line_id → invoice_line (nullable) Important fields: description, qty, unit_price, line_total Unique: n/a Classification: T

F.7 — CUSTOMER LEDGER (Accounts Receivable — event-sourced, mirrors the inventory-ledger pattern per Domain-Model correction #1: balances are never directly editable)

M13 — customer_ledger Purpose: One account header per customer; running balance is a read-optimized cache only, never the source of truth (same relationship inventory_balance_snapshot T3 has to inventory_transaction T1). PK: id FK: customer_id → customer (1:1) Important fields: current_balance (derived cache), currency_id → currency, last_reconciled_at, last_entry_seq Unique: customer_id Business constraints: non-authoritative — must always equal SUM(customer_ledger_entry.signed_amount) for the customer; fully rebuildable from the ledger Classification: V (projection, non-authoritative)

T22 — customer_ledger_entry Purpose: Immutable, append-only accounts-receivable ledger — the actual source of truth for customer balances (invoice = debit, payment/credit_note = credit). PK: id FK: customer_ledger_id → customer_ledger, reference_type + reference_id (polymorphic: invoice | payment | credit_note), actor_user_id → app_user Important fields: sequence_no (monotonic per customer), signed_amount (+debit / −credit), currency_id → currency, occurred_at (UTC), entry_type (INVOICE_ISSUED/PAYMENT_RECEIVED/CREDIT_NOTE_APPLIED/WRITE_OFF), row_hash, prev_hash Unique: sequence_no per customer_ledger_id Business constraints: append-only, no UPDATE/DELETE; corrections = compensating entry only; hash-chain integrity mirrors T1 inventory_transaction Classification: T + H (immutable ledger)

PART H — DESIGN-CONSISTENCY ADDENDUM (why some items on this continuation's requested list were not re-created as new tables)

Payment History — not added. payment (T19) was already specified as immutable once posted, with corrections made only via a compensating reversal payment, never an in-place edit — i.e. payment is already its own event-sourced ledger, the same pattern as inventory_transaction and commission_transaction. A companion history table would log transitions that, by construction, never occur in place. If the business later needs a payment clearing lifecycle (PENDING→CLEARED→BOUNCED), the correct extension is a new append-only payment_clearance_event table, not a retrofit of mutability into the approved T19 — flagged as an open question rather than resolved unilaterally, since T19 is an already-approved prior section.
Commission History — not added, for the identical reason: commission_transaction (T23) is already event-sourced (accrual/approval/payment/clawback are each their own immutable row). That structure is itself the history.
Return Approval — not added as its own table. Reuses the existing generic approval_request (T25) / approval_history (H7) pair with entity_type='customer_return', consistent with how order overrides, stock adjustments, and stock transfers already share that same polymorphic approval workflow.
Approval / Approval History — already present from the prior pass (T25 / H7); not recreated.
Invoice / Invoice Line / Invoice History / Payment / Payment Allocation / Commission / Notification / Bot Message Log / Audit Log / Attachment — already present from the prior pass (T17, T18, H4, T19, J2, T23, T24, H5, H6, M14 respectively); not recreated, per the "do not regenerate previous sections" instruction.

PART J — AGGREGATE MAPPING (DDD Aggregate Roots and Boundaries)

Product (root: product) — owns product_lot, product_serial, product_image. Invariant: SKU immutability once shipped against. Warehouse (root: warehouse) — owns warehouse_location. Invariant: cannot deactivate with non-zero stock. Representative (root: representative) — owns representative_contact, bot_session, commission_config. Does NOT own commission_transaction (see below — ledger streams are their own consistency boundary, not nested inside the actor aggregate). Customer (root: customer) — owns customer_contact. Independent aggregate per Domain-Model correction #2; does NOT own invoice/order (those reference customer_id but are their own roots). InventoryLedger (root: inventory_transaction, conceptually a stream keyed by warehouse+product+lot, not a single row) — inventory_balance_snapshot and stock_reservation read/depend on it but are not inside its transactional boundary. StockTransfer (root: stock_transfer) — owns transfer_line, transfer_history. StockAdjustment (root: stock_adjustment) — single-row aggregate; posts to InventoryLedger on APPLIED. PhysicalCount (root: physical_count) — owns physical_count_line. Order (root: order) — owns order_line, order_status_history, stock_reservation (via order_id). Invariant: state machine transitions guarded (§ Part F.4). Shipment (root: shipment) — owns shipment_line, shipment_status_history. Invoice (root: invoice) — owns invoice_line, invoice_history. References order via invoice_order but does not own it. Payment (root: payment) — single-row append-only aggregate; payment_allocation is a resolving join, conceptually shared between Payment and Invoice aggregates (a deliberate cross-aggregate join, acceptable because allocated_amount is itself an immutable fact once posted). CreditNote (root: credit_note) — owns credit_note_line. CustomerLedger (root: customer_ledger, stream = customer_ledger_entry) — same "ledger is the aggregate, header is a cache" pattern as InventoryLedger. PART K — INDEX RECOMMENDATIONS

Beyond the Unique constraints already specified per table:

inventory_transaction: composite (warehouse_id, product_id, lot_id, sequence_no) for balance projection; (reference_type, reference_id) for tracing a transaction back to its source document.
customer_ledger_entry / commission_transaction: composite (customer_ledger_id, sequence_no) and (representative_id, sequence_no) respectively — same rationale as the inventory index.
order: (customer_id, state), (representative_id, state) — dashboard/queue queries.
invoice: (customer_id, state), (due_at) partial index where state IN (ISSUED, PARTIALLY_PAID) for AR aging.
payment_allocation: (invoice_id), (payment_id) — both directions of the N:N are queried independently.
shipment: (tracking_number), (state) partial index where state NOT IN (DELIVERED, FAILED) for active-shipment dashboards.
audit_log: (entity_type, entity_id, occurred_at) — the dominant "show me the history of this record" query.
notification: partial index on (state) where state = 'QUEUED' for the delivery worker's polling query.
approval_request: partial index on (status) where status = 'PENDING', plus (entity_type, entity_id).
product / customer / representative / warehouse: unique index on code/sku already implied; add trigram/full-text index on name for search-as-you-type UI.
bot_message_log / notification_history / report_snapshot / kpi_snapshot: (occurred_at)/(captured_at) B-tree, primarily to support range scans within partitions (see PART L).

PART L — PARTITIONING RECOMMENDATIONS

Time-based range partitioning (by occurred_at/event_at, monthly for high-volume, quarterly for lower-volume) recommended for: inventory_transaction, customer_ledger_entry, commission_transaction, audit_log, bot_message_log, notification_history, order_status_history, invoice_history, shipment_status_history, transfer_history, approval_history. Additional list/hash sub-partitioning by warehouse_id recommended for inventory_transaction specifically if the deployment scales past a handful of warehouses per factory network, since nearly all reads are warehouse-scoped. Row-level security (already noted in 08_Architecture.md for rep scoping) pairs naturally with representative_id list partitioning for commission_transaction and bot_message_log at very large rep-count scale, but is not needed at the roadmap's stated mid-size scope. report_snapshot and kpi_snapshot: range partition by captured_at with an aggressive retention/rollup policy (e.g. daily granularity kept 90 days, then rolled up to weekly) since these are dashboard-support tables, not system-of-record. order/invoice/shipment (mutable master transactional tables, not pure ledgers): partitioning is optional; if used, partition by created/issued year with older partitions marked read-only/archival rather than physically moved, to preserve FK integrity with invoice_line/shipment_line.

PART M — SCALABILITY NOTES

The three ledger aggregates (inventory_transaction, customer_ledger_entry, commission_transaction) all share the same hash-chain + sequence_no verification cost profile; a single shared reconciliation/verification background service (per PART G.3 risk #3) avoids triplicated operational tooling as volume grows.
inventory_balance_snapshot, customer_ledger, and kpi_snapshot are all non-authoritative caches — all three should be refreshed asynchronously off the event bus (RabbitMQ per 08_Architecture.md) rather than synchronously on every ledger write, to keep write-path latency flat as transaction volume grows.
Read replicas are recommended for reporting/report_snapshot/kpi_snapshot generation specifically, isolating analytical scan load from the operational write path (order/invoice/inventory_transaction).
The polymorphic (entity_type, entity_id) pattern used across audit_log, approval_request, attachment, generated_document, and customer_ledger_entry.reference will not scale well as a single unindexed JSONB blob — each should carry its composite index (PART K) and, at very large scale, may warrant being split into per-type partitioned tables sharing a common interface rather than one unbounded polymorphic table.
Archival strategy: closed orders/invoices/shipments older than a policy-defined window (e.g. 3–5 years) should move to cold/columnar storage (e.g. Parquet on S3-compatible storage, consistent with the existing MinIO/S3 file-storage choice in 08_Architecture.md) rather than living indefinitely in the OLTP partitions.
Bot messaging (bot_message_log) and notifications (notification, notification_history) are the highest-cardinality, lowest-business-value-per-row tables in the model — these are the first candidates for a shorter retention policy or a cheaper storage tier if volume becomes a cost concern.
